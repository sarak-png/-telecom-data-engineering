# Phase 2 — local, repeatable ingestion

This phase adds validated local ingestion for the existing TRA traffic dataset.
There is no Snowflake connection. The original CSV remains read-only to the code.
Python 3.11 runs in the dedicated `telecom_de` Conda environment.
See [actual execution and test results](archive/phase2-verification.md).

## Execute

From the repository root in an Anaconda Prompt or Conda-enabled terminal:

```powershell
conda activate telecom_de
python -m pip install -r requirements.txt
python -m telecom_pipeline.pipeline data/raw/tra-open-data-traffic.csv
python -m telecom_pipeline.pipeline data/raw/tra-open-data-traffic.csv
python -m pytest -q
```

Install only when preparing an environment or changing dependencies. The added
Excel dependency, `openpyxl` 3.1.5, was installed into `telecom_de` after approval.
The pipeline also uses Python's built-in SQLite, Decimal, logging, hashlib, and
uuid modules, avoiding additional infrastructure for this local stage.

Without activating Conda, target the dedicated environment explicitly:

```powershell
conda run --no-capture-output -n telecom_de python -m telecom_pipeline.pipeline data/raw/tra-open-data-traffic.csv
```

The Phase 1 inspection CLI remains available:
`python -m telecom_pipeline.ingestion data/raw/tra-open-data-traffic.csv`.

## Input contracts

- TRA CSV: strict UTF-8 with optional BOM, comma delimiter, the observed comment
  preamble and bilingual headers. The existing reader still retains Arabic labels.
- Plain CSV: first row is the nine English headers in documented source order;
  no metadata or Arabic header row. Quoted commas are supported. Invalid widths
  and duplicate headers are rejected. An explicit `--encoding cp1252`, for example,
  is available only when that source encoding has been verified.
- Excel: `.xlsx`, first worksheet by default, or `--sheet Traffic` for a named
  worksheet. Row 1 must contain the nine English headers; records begin on row 2.
  Literal values only. Formulas, legacy `.xls`, and arbitrary report layouts are
  rejected. Numeric Excel cells have already been interpreted by Excel; use text
  cells where exact original decimal formatting matters.
- Blank records are skipped. The input is read once into a byte snapshot, and
  its SHA-256 identifies the exact bytes parsed. Raw files are never rewritten.

Example: `python -m telecom_pipeline.pipeline path/to/export.xlsx --sheet Traffic`.
No Excel file is claimed as an authentic TRA source; Excel tests use explicitly
synthetic temporary fixtures generated by pytest.

## Validation and normalization

`validation.py` declares the schema discovered in Phase 1, rather than inferring
types from a few rows. All batches must match the exact nine-column schema/order.

| Check | Policy |
| --- | --- |
| Year | Required integral number, 1900–2100 (explicit project contract) |
| Quarter | Required integral number, 1–4 |
| Seven metrics | Nullable, finite nonnegative decimal numbers |
| Missing metric | Retain null and count it; never fill with zero |
| Exact/normalized duplicates | Count and retain one unique observation per batch |
| Same period, different values within one input | Reject the whole batch |
| Metadata record count mismatch | Report a warning and retain actual data rows |
| Invalid structure, schema, types, or required keys | Reject the whole batch |

Decimal parsing avoids binary-float rounding. Normalization trims whitespace,
removes valid thousands separators, and removes insignificant decimal zeros.
For example `2,026.00` becomes `2026` and `120.520` becomes `120.52` in the local
record payload only. Metrics stay exact decimal strings or null in JSON, rather
than becoming SQLite floating-point values. Source columns and measurement units
are preserved. Scientific notation and malformed separators are rejected.

## Storage, batches, and safe reruns

By default, derived state lives in `data/ingestion/ingestion.sqlite3`, excluded
from Git. Use `--state-dir path/to/state` to choose another directory outside
the input's directory. Always reuse the same state directory for repeatable runs.

SQLite supplies transactional writes and uniqueness constraints without running
a database server. This is local ingestion state, not the later warehouse.

| Table | Purpose |
| --- | --- |
| `batches` | UUID, source path/hash, UTC start/end timestamps, status, JSON quality report or error |
| `records` | SHA-256 of canonical record payload, exact decimal JSON, first batch and ingestion time |
| `batch_records` | Links each successful batch to all its unique observations, including already stored records |

Records and successful batch completion commit in one transaction. Exceptions
roll back partial records, and a separate update records FAILED. New invocations
get new batch IDs even when they insert no records. The primary key prevents
duplicate observations across reruns, files, and supported formats. A changed
record in a later file becomes another immutable observation; this phase does
not choose a latest value, overwrite a period, or implement warehouse MERGE.

The ledger must be retained and backed up to preserve deduplication history.
A different/empty state directory starts independent ingestion history. SQLite
supports local concurrent writers using a 30-second lock timeout; this is not a
distributed ingestion system. A hard process termination can leave a RUNNING
batch in history; rerunning is safe, but automatic stale-run reconciliation is
deferred. Initialization failures before the ledger opens cannot be recorded in
that ledger; the CLI still exits nonzero and prints the error.

## Structured logs and monitoring

CLI events are JSON lines on stderr: `batch_started`, `batch_succeeded`, and
`batch_failed`. They include UTC timestamps, batch IDs, source identity, counts,
and error details where applicable. Failures use ERROR level, propagate from the
Python API, and produce CLI exit code 1. Successful reports print as JSON on
stdout. Batch history is persisted in SQLite even without redirecting logs.

To preserve event logs for a run:

```powershell
python -m telecom_pipeline.pipeline data/raw/tra-open-data-traffic.csv 2> phase2-events.jsonl
```

To inspect history using Python (no sqlite CLI required):

```powershell
python -c "import sqlite3; c=sqlite3.connect('data/ingestion/ingestion.sqlite3'); print(c.execute('SELECT batch_id,status,started_at,finished_at FROM batches ORDER BY started_at').fetchall()); c.close()"
```

## Modules

- `ingestion.py`: Phase 1 reader; now also exposes a byte-snapshot parser.
- `readers.py`: format dispatch and strict CSV/Excel layout handling.
- `validation.py`: schema, null/numeric/business checks, duplicate handling.
- `store.py`: SQLite tables and transactional record persistence.
- `pipeline.py`: orchestration, batch lifecycle, logging, and CLI.
- `tests/test_pipeline.py`: synthetic fixtures and real-source integration tests.

No notebooks are required to execute the ingestion pipeline. Later phases can
reuse these readers and contracts while adding warehouse-specific storage.
